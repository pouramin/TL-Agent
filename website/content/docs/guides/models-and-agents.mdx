Kilo Local UI does not implement its own model router. It asks the local Kilo runtime which product agents, providers, and models are available and keeps provider/model execution inside Kilo.

## Agents

For the pinned Kilo `7.6.2` runtime, the primary UI reads the product agent route used by Kilo's official client.

This distinction matters: Kilo builds base agents internally and its product layer patches them for the user-facing coding experience. In particular, the product layer exposes **`code`** rather than leaking the raw internal **`build`** agent as the main coding agent.

Kilo Local UI uses the agent's stable `name` for selection and can use `displayName` when Kilo provides one for presentation.

## Providers and models

Provider state comes from Kilo's production provider surface. It reports the provider catalog, defaults, connected providers, and failures. Models are enumerated from the models exposed under those providers, matching the product path used by Kilo's current client.

The UI can keep a convenient browser-side model selection, but the adapter converts it to the product model reference expected by Kilo:

```json
{
  "providerID": "provider-id",
  "modelID": "model-id"
}
```

## Kilo account login

Kilo Local UI exposes Kilo's normal device authorization flow. After login, provider state is refreshed through Kilo. Credentials, provider configuration, and model execution remain Kilo/provider responsibilities rather than a cloud service operated by this project.

## Why this boundary matters

Keeping agent/provider/model behavior inside Kilo avoids creating a second abstraction that can drift away from the runtime. The browser adapter is the compatibility boundary when Kilo's product API changes.
