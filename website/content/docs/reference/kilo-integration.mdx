Kilo Local UI pins its integration to a specific Kilo runtime and verifies the **actual product-facing coding API used by Kilo's official client** for that version.

The current project targets Kilo Code `7.6.2`.

## Why “Protocol v2” is not enough

Kilo `7.6.2` exposes more than one API generation. The SDK package includes the current product HTTP API used by Kilo's official coding client as well as an experimental `/api/*` Protocol v2 surface.

Those surfaces are not interchangeable in this version. Real runtime testing found meaningful differences in agent behavior and session execution. The rule for Kilo Local UI is therefore:

> The primary coding path follows the same generated SDK methods that the official Kilo client actually uses for the pinned version.

The experimental `/api/*` surface is not mixed into the primary session model unless upstream migrates its product client and runtime parity is verified.

## Product routes

The compatibility adapter covers product-facing operations for:

- runtime health and project path;
- agents;
- providers and models;
- sessions and session status;
- projected messages;
- asynchronous prompting and abort;
- global project-scoped events;
- permissions and questions;
- Kilo account OAuth/device authorization.

Every project-scoped request carries the selected `directory` explicitly. The launcher also injects its directory header at the reverse-proxy boundary.

## One browser adapter

All browser-side Kilo calls are centralized in:

```text
cmd/launcher/web/kilo-api.js
```

UI modules should not construct Kilo endpoint paths directly. The adapter owns directory routing, response normalization, model-reference conversion, product endpoints, event-envelope unwrapping, permissions/questions, and Kilo OAuth.

That makes a future Kilo upgrade an explicit compatibility change instead of a set of scattered UI edits.

## Messages and events

The production session message shape for this runtime uses an `info + parts` envelope. Projected messages are the reconnect-safe source of truth.

Live activity comes from Kilo's project-scoped global SSE stream. The adapter unwraps the global event envelope before the UI sees product events such as message updates, session status changes, permission/question events, and file edits. Polling of status/messages remains a conservative fallback after prompts.

## Automated compatibility gates

CI is designed to download the exact Kilo binary pinned by `KILO_VERSION` and test the real runtime through Kilo Local UI. The product contract gate verifies the product agent/provider/session/message/permission/question/event shapes and project routing.

A separate end-to-end test drives the real Kilo write tool against a local fake OpenAI-compatible provider, then verifies both the file written inside the selected project and the final assistant result. This keeps the compatibility claim tied to an executable test rather than documentation alone.

## Upgrade rule

Before changing `KILO_VERSION`, the official client's actual SDK calls, product agent patching, message/part schemas, adapter behavior, and real-runtime tests must be reviewed. A release should not be cut just because a new Kilo binary starts successfully.
