TL Studio owns Provider definitions, model discovery, the model catalog shown in the product, and Provider credentials.

Released behavior and development-preview behavior are labeled separately below.

## Native model protocols

| Protocol | Stable v0.5 | Development v0.6 |
| --- | --- | --- |
| OpenAI-compatible Chat Completions | ✅ | ✅ |
| OpenAI Responses | ✅ | ✅ |
| Anthropic Messages | ✅ | ✅ |
| Google Gemini generateContent | — | ✅ |

Model requests go directly from TL Studio to the configured Provider endpoint.

## Custom Provider setup

The 0.6 setup stays discovery-first. For a normal custom Provider you provide:

- API address;
- API type: OpenAI-compatible or Anthropic-compatible;
- API key.

TL Studio then attempts model discovery automatically. Manual Model ID entry remains an explicit fallback for private or unlisted Models.

Existing OpenAI Responses Provider definitions remain editable for compatibility with saved configurations.

## Discover Models

When the Provider exposes a model-list API, TL Studio validates the Base URL, sends the discovery request, normalizes the returned Models, and presents a searchable catalog.

Normalized metadata can include:

- Model ID and name;
- context/output limits;
- Tool Calling;
- Reasoning;
- Vision;
- Router kind.

## Discovery safety

Provider discovery:

- accepts valid HTTP(S) Base URLs without embedded credentials;
- uses a bounded request timeout;
- limits catalog response size;
- caps normalized catalog size;
- blocks unsafe cross-origin redirect behavior;
- uses bounded pagination where supported.

Authentication failures remain explicit and are not hidden behind stale cache.

## Provider registry

Saved definitions live in:

~~~text
providers.json
~~~

The registry stores Provider metadata and Model definitions. It does not contain API keys or OAuth tokens.

## Credential vault

Manual API credentials and account credentials use separate vault slots.

A connected account can take precedence while active, but signing out does not delete the user's existing manual API key.

Secrets do not appear in Browser storage or normal Provider JSON state.

## Provider connection modes — v0.6 development preview

| Provider | Default setup | Integration |
| --- | --- | --- |
| **ChatGPT / Codex** | ✅ Account sign-in | Official Codex login, ChatGPT-plan model discovery, isolated Codex provider bridge |
| **GitHub Copilot** | ⏳ Account sign-in | Account slot is reserved; the model path remains deferred |
| **Claude / Anthropic** | ✅ API key | Anthropic Messages API preset |
| **Google / Gemini** | ✅ API key | Google's documented OpenAI-compatible Gemini API preset |
| **Hugging Face** | ✅ API token | OpenAI-compatible Inference Providers preset |
| **OpenRouter** | ✅ API key | OpenAI-compatible OpenRouter preset |

API-based cards open the existing discovery-first Provider editor with the endpoint and protocol already filled in. They are not disabled just because they do not use consumer-account OAuth.

ChatGPT authentication is owned by OpenAI's official Codex client inside a TL Studio-specific isolated `CODEX_HOME`. TL Studio does not read or copy raw ChatGPT OAuth tokens, browser cookies, private session tokens, or undocumented backend credentials.

For ChatGPT-plan model turns, TL Studio uses the official Codex CLI in an empty temporary working directory with user/project Codex config ignored, a read-only sandbox, approval policy `never`, and web search disabled. Structured bridge output becomes either assistant text or TL Studio Tool calls; Tool execution and Permission decisions still happen inside TL Studio.

If `codex` is not available on PATH, the alpha can use `npx @openai/codex`, or the user can configure an explicit Codex executable path in Provider Settings.

## Gemini setup

During the current alpha, Gemini account login requires two non-secret setup values:

~~~text
Google Cloud Project ID
Desktop OAuth Client ID
~~~

They can be configured from Provider Settings.

OAuth access and refresh tokens stay only in the TL Studio credential vault.

Each sign-in starts a temporary listener bound to:

~~~text
127.0.0.1:<random-port>
~~~

The listener validates OAuth state, completes the PKCE flow, and shuts down after success, cancellation, or expiry.
