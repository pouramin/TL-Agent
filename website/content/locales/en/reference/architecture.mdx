TL Studio is a **single local application** with embedded Browser assets and a native coding-agent core.

The current public release is v0.5.0. Development v0.6.0-alpha.1 extends the Provider boundary with account-backed integrations without changing the Agent architecture.

~~~text
Browser Workspace
        │ same local control origin
        ▼
TL Studio Go Launcher / Local Core
  ├─ Workspace + Project filesystem
  ├─ Project Search
  ├─ Terminal / Process Manager
  ├─ Preview Manager
  ├─ Provider Registry + Model Discovery
  ├─ Credential Vault
  ├─ Provider Account adapters
  ├─ Session Domain + Persistence
  ├─ Question Manager
  ├─ Permission Engine
  ├─ Semantic Event Bus
  ├─ Tool Registry + Tool Executor
  ├─ Plugin Manager + MCP clients
  └─ Native Agent + direct Model clients
        │
        ├─ configured Provider endpoints
        └─ enabled local MCP processes

Previewed Project content
        └────────► separate loopback origin
~~~

## Startup model

Normal startup:

1. resolves the selected Project;
2. creates TL Studio application state;
3. initializes product services;
4. binds the control server to loopback;
5. opens the Browser unless no-browser mode is requested.

The Browser communicates directly with TL Studio-owned local product domains.

## Browser boundary

Important Browser-facing local surfaces include:

~~~text
/local/status
/local/health
/local/project
/local/providers/*
/local/provider-accounts*
/local/sessions*
/local/questions*
/local/permissions*
/local/events
/local/plugins*
/local/tools
/local/search
/local/process*
/local/preview*
~~~

Browser source is strict TypeScript under cmd/launcher/ui and is bundled with esbuild. Monaco and its workers are bundled locally.

## Native Agent

The Agent path is TL Studio-owned:

~~~text
Browser Session Run
→ Session Domain
→ Native Agent
→ selected Provider
→ Model response
→ optional Tool call
→ Permission / Question handling when needed
→ Tool Executor or MCP Plugin
→ structured Tool result
→ Provider continuation
→ final response
→ Session persistence + Event Bus
~~~

Unsupported Provider protocols or capabilities fail explicitly.

## Sessions, Questions, Permissions, Events

TL Studio owns Session creation, selection, rename/delete, run/abort, status, Messages, activity, usage metadata, Changes, and persistence.

interaction.question pauses the Agent and registers a Session-scoped Question.

Permission requests and remembered Project-scoped rules are owned by the Permission Engine.

Both produce semantic events through the local Event Bus.

## Providers and credentials

The Provider Registry owns Provider definitions, configured Models, model discovery, catalog cache, and direct model execution.

Credentials live separately in the TL Studio credential vault and do not appear in providers.json or Browser storage.

### Provider Account domain

Development v0.6 adds typed Provider Account adapters for:

- OpenRouter;
- Hugging Face;
- Google / Gemini.

The generic lifecycle includes status, begin/complete login, polling where needed, cancellation, refresh, credential resolution, model discovery, and disconnect.

Manual API credentials and account credentials use separate vault slots.

Browser code receives only semantic account state and safe login instructions. OAuth codes, PKCE verifiers, access tokens, refresh tokens, API keys, cookies, and client secrets stay on the Go side.

### Gemini desktop loopback

Each Gemini sign-in starts a temporary HTTP listener bound only to:

~~~text
127.0.0.1:<random-port>
~~~

The callback validates OAuth state and shuts down after completion, cancellation, or expiry.

## Tools and Plugins/MCP

Built-in Tools cover project files, Search, Terminal commands, and interactive Questions.

Enabled stdio MCP Plugins can add dynamic Tool definitions. Plugin tools enter the same Tool Registry and Permission system before execution.

## Preview isolation

Preview is a separate local trust boundary.

Static/file content is served on a different loopback origin from the TL Studio control server. Supported dev-server Preview accepts loopback URLs only.

## State and storage

TL Studio stores product state under its local application state directory, including Provider definitions, credentials, Sessions, Permission rules, Plugin configuration/secrets, model-catalog cache, Provider Account setup, and preferences.

Secrets remain separated from normal JSON configuration.

## Zero-infrastructure rule

TL Studio does not require a project-owned application backend, database, telemetry collector, model proxy, or hosted workspace.

Network traffic comes from explicit user configuration such as model Providers or MCP processes.
