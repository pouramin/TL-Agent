TL Agent is built around a local product layer and a replaceable agent-runtime boundary.

```text
Browser workspace
  ↓ localhost
TL Agent UI + Go launcher
  ├─ project picker
  ├─ project files / search / terminal / preview
  ├─ provider/model registry
  ├─ provider settings + recovery UX
  ├─ local state + appearance preferences
  ├─ security boundary
  └─ authenticated runtime adapter
       ↓
Bundled agent runtime
       ├─ sessions / agents / tools
       ├─ local credential store
       ├─ provider execution / model inference
       └─ agent project execution
```

## TL Agent owns

- the standalone browser workspace;
- local launch and process lifecycle;
- project selection and project-scoped file/search/process APIs;
- provider/model definitions and their local registry;
- the browser-facing `/runtime/*` contract;
- the reverse-proxy/security boundary;
- packaging, releases, and the TL Agent brand;
- user-facing session, files, changes, permission, provider-settings, recovery, preview, and appearance UX.

## Runtime owns today

The bundled runtime still handles agent execution, tool execution, session internals, runtime-originated filesystem/tool calls, provider credentials, and model execution.

Some semantics such as sessions, tools, and permissions still originate in the runtime today, but the browser reaches them only through the TL Agent runtime boundary. Future ownership can move inward without redesigning the product UI.

The distinction is architectural rather than product-facing: users operate **TL Agent** while engine-specific implementation details stay behind the adapter boundary.
