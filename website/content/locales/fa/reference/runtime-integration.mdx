TL Agent جزئیات مخصوص Engine را پشت Runtime Adapter نگه می‌دارد. نسخه Stable فعلی **Kilo Code 7.6.2** را به‌عنوان Agent Engine شخص ثالث و تست‌شده Bundle می‌کند، اما Workflow عادی کاربر و قراردادهای Browser متعلق به خود TL Agent هستند.

## Product Boundary

فراخوانی‌های Runtime در Browser از Namespace خود TL Agent عبور می‌کنند:

`/runtime/*`

Source اصلی Adapter:

`cmd/launcher/ui/runtime-api.ts`

و JavaScript تولیدشده:

`cmd/launcher/web/runtime-api.js`

بخش‌های UI نباید Route prefix، Authentication، Provider package یا OAuth مخصوص Engine را مستقیم بسازند.

## مالکیت Provider و Model

تعریف Custom Provider و Model داخل Registry محلی خود TL Agent ذخیره می‌شود:

`providers.json`

Launcher این تعریف‌ها را در پشت صحنه برای Engine فعال ترجمه می‌کند.

Credentialهای Provider فعلاً داخل Local Credential Store مربوط به Runtime باقی می‌مانند. این وابستگی با مالکیت Provider/Model Definition یکی نیست و می‌تواند در Milestone امنیتی جداگانه منتقل شود.

## Compatibility Contract

نسخه Engine همراه برنامه Pin می‌شود و CI، Project Routing، Agent، Session، Message، Async Prompt، Global Event، Permission، Question، Provider Translation و یک Write Tool واقعی را از طریق مرز عمومی Runtime خود TL Agent تست می‌کند.

جزئیات دقیق Engine فعلی همچنان داخل فایل داخلی زیر مستند می‌شود:

`docs/KILO_API_CONTRACT.md`

چون آن فایل قرارداد پیاده‌سازی فعلی است، نه Product API عمومی TL Agent.

## قانون Upgrade

قبل از تغییر نسخه Engine، Target جدید باید از Runtime Boundary و Product E2E خود TL Agent عبور کند. تغییرات مخصوص Engine تا حد ممکن باید پشت Launcher/Runtime Adapter باقی بمانند.
