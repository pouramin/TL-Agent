تعریف Provider، Model Discovery، Model Catalog و Credentialهای Provider در اختیار خود TL Studio هستند.

رفتار Stable و Development Preview در ادامه جدا از هم مشخص شده است.

## Protocolهای Native مدل

| Protocol | Stable v0.5 | Development v0.6 |
| --- | --- | --- |
| OpenAI-compatible Chat Completions | ✅ | ✅ |
| OpenAI Responses | ✅ | ✅ |
| Anthropic Messages | ✅ | ✅ |
| Google Gemini generateContent | — | ✅ |

Model Request مستقیماً از TL Studio به Endpoint تنظیم‌شدهٔ Provider می‌رود.

## راه‌اندازی Provider سفارشی

در نسخهٔ 0.6 راه‌اندازی Provider سفارشی Discovery-first باقی مانده است. در حالت عادی فقط این موارد وارد می‌شوند:

- API Address؛
- API Type از نوع OpenAI-compatible یا Anthropic-compatible؛
- API Key.

بعد از آن TL Studio تلاش می‌کند مدل‌ها را به‌صورت خودکار Discover کند. ورود دستی Model ID فقط Fallback صریح برای مدل خصوصی یا فهرست‌نشده است.

Providerهای قدیمی از نوع OpenAI Responses همچنان قابل ویرایش باقی می‌مانند.

## Model Discovery

اگر Provider دارای Model-list API باشد، TL Studio آدرس را Validate می‌کند، Discovery Request می‌فرستد، Modelها را Normalize می‌کند و Catalog قابل Search می‌سازد.

Metadata قابل استفاده می‌تواند شامل این موارد باشد:

- Model ID و Name؛
- Context/Output Limit؛
- Tool Calling؛
- Reasoning؛
- Vision؛
- Router Kind.

## امنیت Discovery

Provider Discovery:

- فقط HTTP(S) Base URL معتبر و بدون Embedded Credential را قبول می‌کند؛
- Timeout محدود دارد؛
- اندازهٔ Response Catalog را محدود می‌کند؛
- تعداد Modelهای Normalize‌شده را محدود می‌کند؛
- Redirect ناامن بین Originها را Block می‌کند؛
- در Endpointهای صفحه‌بندی‌شده از Page Count محدود استفاده می‌کند.

Authentication Failure به‌صورت صریح باقی می‌ماند و با Cache قدیمی پنهان نمی‌شود.

## Provider Registry

Definitionهای ذخیره‌شده داخل این فایل هستند:

~~~text
providers.json
~~~

Registry فقط Metadata و Model Definition را نگه می‌دارد و API Key یا OAuth Token داخل آن قرار نمی‌گیرد.

## Credential Vault

Credential دستی API و Credential حساب در Slotهای جداگانه نگهداری می‌شوند.

اتصال حساب می‌تواند در زمان فعال بودن اولویت داشته باشد، اما Sign out کردن حساب API Key دستی موجود را حذف نمی‌کند.

Secretها وارد Browser Storage یا Provider JSON عادی نمی‌شوند.

## Providerهای حسابی — Development Preview نسخهٔ 0.6

| Provider | وضعیت | Integration |
| --- | --- | --- |
| **OpenRouter** | ✅ فعال | OAuth + PKCE رسمی، Credential حساب و Model Discovery |
| **Hugging Face** | ✅ فعال | Public-client OAuth + PKCE، Refresh و Inference Providers Discovery |
| **Google / Gemini** | ✅ فعال | Installed-app OAuth + PKCE، Refresh/Revocation و Transport بومی Gemini |
| **ChatGPT / Codex** | ⏳ Deferred | سطح رسمی فعلی Model Access با مرز Native Model Loop پروژه سازگار نیست |
| **Claude account** | ⏳ Deferred | منتظر قرارداد عمومی و مستند برای Third-party Consumer Account Authorization |
| **GitHub Copilot** | ⏳ Deferred | مسیر رسمی فعلی Model Access همچنان به Copilot SDK/runtime وابسته است |

Providerهای Deferred عمداً در Settings دیده می‌شوند و به‌عنوان Runtime Credential Source ثبت نمی‌شوند.

## تنظیم Gemini

در Alpha فعلی، Account Login مربوط به Gemini به دو مقدار غیرمحرمانه نیاز دارد:

~~~text
Google Cloud Project ID
Desktop OAuth Client ID
~~~

این مقادیر از Provider Settings قابل تنظیم هستند.

Access Token و Refresh Token فقط داخل Credential Vault خود TL Studio باقی می‌مانند.

برای هر Sign-in یک Listener موقت روی این آدرس ساخته می‌شود:

~~~text
127.0.0.1:<random-port>
~~~

Listener مقدار OAuth state را بررسی می‌کند، Flow مبتنی بر PKCE را کامل می‌کند و پس از موفقیت، لغو یا Expiry بسته می‌شود.
